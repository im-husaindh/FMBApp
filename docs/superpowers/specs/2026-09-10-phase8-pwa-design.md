# FMBRequestThali — Phase 8: PWA Design

Source spec: `FMBRequestThali Web App — Complete Development Prompt.md` §1 "Application Type" (~line 70-84: "Build the website as a responsive Progressive Web App... Allow supported mobile users to install it to their home screen"), §38's "PWA Settings" bullet (~line 1499, among centrally-stored business configuration), §40's "offline-friendly messaging" requirement (~line 1534), build sequence item 20. Builds on Phase 1's `app_settings` table/`src/lib/settings` read-only helper (unchanged by this phase) and every prior phase's shipped UI (unchanged except `src/app/layout.tsx`).

## Why this shape

This app's Next.js version (16.3.4) ships built-in, non-experimental file conventions for exactly what a PWA needs — `app/manifest.ts` for the Web App Manifest and code-generated `icon.tsx`/`apple-icon.tsx` routes via `next/og`'s `ImageResponse` — so no third-party PWA library (next-pwa, Serwist, etc.) is needed for installability. The spec's actual ask is installability plus "offline-friendly messaging" (a UX/communication requirement), not "the app must fully function with zero network" — so this phase deliberately stops short of full service-worker-based offline page caching, which would be a large addition beyond what's asked and would need its own design (cache invalidation strategy, which routes to precache, staleness handling for a live meal-request app where stale data is actively harmful).

Two forks were resolved with the user before writing this spec:
- The manifest's `name`/`short_name` are hardcoded literals matching the seeded `app_settings` values (`app_name: "FMBRequestThali"`, `org_name: "FMB Community"`), not a live DB read — a request-time DB failure degrading the installable manifest is a bad tradeoff for a cosmetic/install-time file, and no `app_settings` write UI exists anywhere in this app to make a live read meaningfully more "centrally sourced" in practice.
- Offline detection uses the plain browser `online`/`offline` events in a client component, not Next 16's new `experimental.useOffline` (which would additionally require flipping `cacheComponents`/`partialPrefetching` repo-wide — a bigger behavioral change than this phase's scope warrants, on features still marked experimental in this version, for a payoff — auto-retrying Server Actions — this app's users would experience mostly as invisible either way once the banner already tells them what's happening).

## Scope

**In Phase 8:**
- `src/app/manifest.ts` — hardcoded Web App Manifest (name, icons, `display: 'standalone'`, theme color matching the app's established blue-600 branding)
- `src/app/icon.tsx` (192×192), `src/app/icon512.tsx` (512×512), `src/app/apple-icon.tsx` (180×180) — code-generated icons via `ImageResponse`, white "FT" monogram on `#2563eb`
- Delete `src/app/favicon.ico` (default, never customized — `icon.tsx` supersedes it)
- `src/components/offline-banner.tsx` — client component, native `online`/`offline` event listeners, renders a dismissed-by-default banner
- `src/app/layout.tsx` — mount `<OfflineBanner />` above `{children}`; fix `metadata.description` from the literal `"Generated by create next app"` to real copy

**Explicitly not in Phase 8:**
- Full service-worker-based offline page caching (e.g. via Serwist) — not what the spec asks for; would need its own cache-invalidation design for a live-data app where stale thali/menu data is actively misleading, not just inconvenient.
- Web Push Notifications — not in the source spec anywhere; this app's Phase 4 "Notifications" requirement is in-app only (a `notifications` table + bell-icon UI), already shipped.
- `experimental.useOffline` / `cacheComponents` / `partialPrefetching` — resolved fork, see above.
- Any `app_settings` write UI, live-sourcing the manifest from the DB, or any other change to `src/lib/settings/index.ts` — out of scope, matches the same reasoning already applied in Phase 7.
- An install-prompt UI component (e.g. a custom "Add to Home Screen" button/banner) — modern browsers already surface their own native install prompt once the manifest + HTTPS + service-worker-or-equivalent criteria are met (the Next.js PWA guide explicitly recommends against a custom `beforeinstallprompt`-based button since it's not cross-platform and doesn't work on Safari iOS at all). This phase makes the app installable; it does not add UI nagging users to install it.

## `src/app/manifest.ts`

```ts
import type { MetadataRoute } from 'next';

export default function manifest(): MetadataRoute.Manifest {
  return {
    name: 'FMBRequestThali',
    short_name: 'FMBRequestThali',
    description: 'Request and manage daily thali meals for FMB Community',
    start_url: '/',
    display: 'standalone',
    background_color: '#ffffff',
    theme_color: '#2563eb',
    icons: [
      { src: '/icon', sizes: '192x192', type: 'image/png' },
      { src: '/icon512', sizes: '512x512', type: 'image/png' },
    ],
  };
}
```

`display: 'standalone'` is what makes "Add to Home Screen" launch without browser chrome — the core of the spec's installability requirement. `theme_color` (`#2563eb`) matches the Tailwind `blue-600` used for every primary button/link across every page shipped this session, so the OS-level install chrome (Android's status bar tint, task switcher card) matches the in-app branding rather than introducing a second, uncoordinated color.

## Icon generation

Three files, each a minimal `ImageResponse` rendering a white, bold "FT" monogram centered on a `#2563eb` background — no external image-editing tool or asset pipeline needed:

```tsx
// src/app/icon.tsx
import { ImageResponse } from 'next/og';

export const size = { width: 192, height: 192 };
export const contentType = 'image/png';

export default function Icon() {
  return new ImageResponse(
    (
      <div
        style={{
          width: '100%',
          height: '100%',
          display: 'flex',
          alignItems: 'center',
          justifyContent: 'center',
          background: '#2563eb',
          color: '#ffffff',
          fontSize: 88,
          fontWeight: 700,
          fontFamily: 'sans-serif',
        }}
      >
        FT
      </div>
    ),
    { ...size }
  );
}
```

`src/app/icon512.tsx` is identical except `size = { width: 512, height: 512 }` and `fontSize: 232` (keeping the glyph-to-canvas ratio consistent with the 192px version). `src/app/apple-icon.tsx` is identical except `size = { width: 180, height: 180 }` (Apple's documented ideal `apple-touch-icon` size) and `fontSize: 82`, and has no `contentType` export needed since `apple-icon` always serves PNG. Each file is fully self-contained — no shared helper module, since three ~20-line files with one differing number each is simpler than a shared component that three call sites would need to import and pass props to for no real reuse benefit at this size.

`icon.tsx` and `apple-icon.tsx` are auto-linked into `<head>` by Next.js (`rel="icon"` and `rel="apple-touch-icon"` respectively) — this is what makes iOS Safari's "Add to Home Screen" pick up a real icon instead of a screenshot thumbnail, since iOS largely ignores the manifest's `icons` array. `icon512.tsx` is not auto-linked as a favicon (Next.js only auto-links one `icon.*` per route segment) but is still reachable at its route URL, which `manifest.ts` references directly for the large manifest icon.

`src/app/favicon.ico` (the unmodified default Next.js favicon, confirmed never customized this session) is deleted in the same change — once `icon.tsx` exists, keeping both is a redundant, conflicting file convention for the same `<link rel="icon">` slot.

## Offline banner

```tsx
// src/components/offline-banner.tsx
'use client';

import { useEffect, useState } from 'react';

export function OfflineBanner() {
  const [isOffline, setIsOffline] = useState(false);

  useEffect(() => {
    setIsOffline(!navigator.onLine);
    const handleOnline = () => setIsOffline(false);
    const handleOffline = () => setIsOffline(true);
    window.addEventListener('online', handleOnline);
    window.addEventListener('offline', handleOffline);
    return () => {
      window.removeEventListener('online', handleOnline);
      window.removeEventListener('offline', handleOffline);
    };
  }, []);

  if (!isOffline) return null;

  return (
    <div role="status" className="bg-amber-50 px-4 py-2 text-center text-sm text-amber-800">
      You&apos;re offline. Some actions won&apos;t work until your connection returns.
    </div>
  );
}
```

`navigator.onLine` is read once on mount (not during server-side render, where `navigator` doesn't exist — the initial state is `false`/hidden, corrected immediately on the client via the `useEffect`, matching this app's existing client-component conventions elsewhere). The `online`/`offline` browser events are well-supported across every platform the spec lists (Android, iOS, Windows, macOS browsers) and need no server round-trip or polling to detect — strictly simpler than reimplementing connectivity detection via failed-request heuristics.

Mounted in `src/app/layout.tsx`:

```tsx
import { OfflineBanner } from '@/components/offline-banner';
// ...
<body className="min-h-full flex flex-col">
  <OfflineBanner />
  {children}
</body>
```

Placed above `{children}` so it's visible on every route this app has — both `(auth)` and `(app)` route groups — without needing to be added to each route group's own layout separately.

## Error handling

Nothing in this phase introduces a new failure mode that needs a red-banner/error-state treatment (this project's established pattern for data-fetching failures) — the manifest and icons are static, build-time-optimized content with no runtime data dependency, and the offline banner has no failure path of its own (worst case, `navigator.onLine`/the event listeners are unsupported in some ancient browser, in which case the banner simply never shows — a silent no-op degradation, not a broken or blank section).

## Testing

- No automated component test for `OfflineBanner`. Checked directly: this repo has zero `.test.tsx` files and no `@testing-library/react`/jsdom/happy-dom dependency or Vitest environment configured anywhere — every existing test targets pure functions or hits a real database (`*.integration.test.ts`), never renders a component. Introducing a whole DOM-testing setup (new dependency, new Vitest environment config) for one 20-line component with no business logic — just two native event-listener bindings and a boolean — fails this project's own YAGNI bar; the manual live verification below (DevTools Network → Offline toggle) is proportionate and sufficient. If a future phase needs real component tests, that setup should be added deliberately for that phase, not smuggled in here for one banner.
- No unit test for the manifest or icon files — they're static declarative output with no branching logic; correctness is verified live (below), not by a unit test asserting on a hardcoded object literal.
- Live verification (manual, post-implementation, not part of the automated suite): run `npm run build && npm start`, then:
  - Fetch the manifest URL directly and confirm valid JSON with both icon URLs resolving to real PNG responses with correct `Content-Type`.
  - Chrome DevTools → Application → Manifest panel: confirm no installability warnings.
  - A Lighthouse PWA audit as a final sanity check on installability criteria.
  - Toggle DevTools → Network → Offline, confirm the banner appears; toggle back online, confirm it disappears.
